# T1–T5 任务分级规则

任务按风险、影响面、不可逆性、需求清晰度和验证成本分级。拿不准时升一级，而不是靠“看起来很小”降级。

| 等级 | 典型任务 | 最小流程 | Git 要求 | 禁止事项 |
| --- | --- | --- | --- | --- |
| T1 微修改 | 已确认文字、颜色、间距、无逻辑影响的显示修复 | Build → Check | 可与紧邻 T1 合并为一个清晰 commit | 不改变数据、状态、导航或已确认视觉结构 |
| T2 小功能 | 单按钮动作、单页小交互、单字段展示 | Spec-lite → Plan → Build → Test | 一个功能一个 commit | 不改变跨模块契约或存储格式 |
| T3 模块 | 独立学习组件、数据适配、一个完整页面流程 | Spec → Plan → Build → Test → Review → LEARN | 独立分支或清晰功能 commit | 未经确认不得扩展为多模块重构 |
| T4 大功能 | Sentence 学习路径、Scene Training、跨模块数据变更 | Research → Spec → Plan → Builder/Reviewer → Test → Review → LEARN | 独立分支、多个原子 commit、合并前审查 | 禁止一句提示直接开工；禁止无回滚方案的数据迁移 |
| T5 新项目 | 新产品、技术路线或目录体系 | Research → PRD → Architecture → Prototype → T4 执行 | 新仓库或主分支外的长期分支 | 禁止先写大功能后补产品定义 |

## 判定问题

任一项回答“是”，至少 T3：

- 会改动多个模块、共享状态、数据结构或导航吗？
- 会影响已有学习进度、课程内容、用户理解或发布承诺吗？
- 是否存在两种以上合理方案，需要 Owner 取舍？
- 是否需要独立审查才有把握发现问题？

任一项回答“是”，至少 T4：

- 是否需要新技术架构、迁移、并行研究或多个 Agent？
- 失败是否会伤及既有稳定版本、核心数据或大量用户路径？
- 验收是否需要内容、教学、视觉和工程四个维度共同判断？

## 各等级产出

- **T1**：改动说明、检查证据。
- **T2**：任务卡、影响文件、测试结果。
- **T3**：任务卡、实施计划、Builder 交付、Reviewer 报告、LEARN 记录。
- **T4/T5**：研究结论、正式规格、阶段计划、风险/回滚、独立审查、验收记录、LEARN 记录。

## 升降级

- 实施中发现需求不清、影响面扩大或数据风险，立即暂停并升级；不能在原等级下硬做。
- 只有在删减范围后，且所有高风险影响已排除，才可降级；降级理由写入任务记录。
